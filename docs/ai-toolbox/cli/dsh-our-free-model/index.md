## 它怎么做到「不要账号不要 Key」

它不是模型服务商，是个**客户端 + 路由器**。README 把出网目标列得很清楚，一共四条车道：

| 车道 | 上游 | 凭据 |
|---|---|---|
| 免费车道 | OpenCode 的免密网关 `opencode.ai/inference/v1/*` | `Bearer public`——这条车道本身就是公开免密额度 |
| Kilo 车道 | Kilo AI 公共网关的免费池（`isFree` 模型） | 无，不需要账号或 Key |
| EAC 车道 | 维护者自建的签名网关 | 加密密封，需 GitHub 登录 + star 本仓库才发令牌 |
| 账号车道 | Qoder、TRAE、Cline、Gemini Code Assist、MiniMax Code、ZCode、LobsterAI、Loomy、Raccoon 等十个 | 你自己的账号登录态 |

真正付钱的是前两条的**上游**。插件做的事是：把这些本来给「人」的免费额度，变成 agent 可以无限调用的接口。

## 成本落在三个地方

「完全免费、不限量」这句话是真的，但它只描述了你这一侧。

**第一，上游的额度。** 免费额度是拉新成本，不是公共服务。被插件规模化调用之后，上游一定会收紧——README 自己写着「随时可能限流、收费或下线」，实测也已经出现地区 403 和超量 429。这类工具的生命周期，基本等于上游发现并封堵的时间。

**第二，你的 prompt。** Kilo 免费池的模型卡原文是：

> Prompts may be logged by the upstream provider and used to improve their services. Not suitable for production or sensitive data workloads.

README 的免责声明也直说：**不要通过免费车道发送密码、密钥、个人身份信息、商业机密，或任何你不愿第三方处理的内容。**

**第三，你的账号。** 那十个账号渠道要登录真实账号，把各家产品的免费额度自动化使用。这些产品各自的条款是否允许这种用法，README 只有一句「上游条款由你遵守」——后果落在账号上，不在插件上。

三笔账里，第二笔最隐蔽：你贴进对话的那段代码、那份日志、那个客户需求，会作为正常推理请求发给一个声明「可能记录用于改进服务」的免费池。

## 工程上它其实很讲究，这恰恰说明风险在哪

读它的安全章节，我的评价是：作者的功力不低，而且很清楚这东西会被怎么打。

- **升级链**：Ed25519 签名清单 → 逐文件 SHA-256 → 暂存回读 → 失败回滚。v1.3.2 专门把公告 `feedUrl` 和升级清单**解耦**，因为在此之前「改一个设置值」等于「在宿主进程里执行任意代码」。
- **公告渲染**：白名单 HTML，用 XSS 语料（脚本注入、事件属性、`javascript:` URL、iframe/svg/form）做测试，全丢。
- **鉴权**：v1.1 修过一次绕过——插件的 `/api/our-free-model` 前缀在宿主的最长前缀分发下优先于内核 `/api`，曾绕过内核鉴权。现在每个请求先过 connection 服务，缺失时退回结构化围栏（回环 Host、拒绝跨站 `sec-fetch-site`、Origin 必须同源），fail closed。
- **本地转发**：只绑回环，把地址改成可路由接口直接返回 400；局域网是另开一扇门，独立的 Key、五条白名单路径、环路保护返回 508。
- **凭据**：0600 文件、`timingSafeEqual` 比对、接口只回显 `hasKey` 和 `…abcd` 指纹。

一个「免费模型插件」写这么多防线，说明作者知道它会招来什么。但工程质量改变不了它的性质——它仍然是一个把别人的免费额度做成长期通道的项目。

## 最危险的一步，在安装那里

README 顶部挂着一条警告，建议每个想装的人都读三遍：

> npm 上那个裸名的 `dsh-our-free-model` **不是本仓库发布的**。它由第三方打包，`index.js`、`client.js` 被改动，并额外包含本仓库从未有过的 `src/channel-visibility.js`。装到它得不到本项目审核过的构建。

正版是带 scope 的 `@ebony-vinyl/dsh-our-free-model`。

这类爆红项目的典型中毒方式，不是代码写坏，是**抢注名字**。当你在搜索引擎或 AI 助手里搜到一个包名就 `npm i`，你装的是谁的代码，取决于谁先注册了那个名字。

## EAC 渠道：把 star 变成凭据

桌面端专属的一条协付通道，设计得相当特别：

- 宿主指纹校验：Tauri 壳的内核路径、内嵌 node、profile 三重信号同时命中才解锁；
- 凭据从不明文出现，只有 AES-256-GCM 密文，解密密钥由散在两个文件里的三片掩码分片即时派生；
- 自建网关**按人计**授权：GitHub 登录 + **已 star 本仓库**才签发专属令牌，网关每 12 小时复查一次 star，取消 star 就在窗口内吊销。

我不评价动机，只说两件事。一是它把「star」变成了「访问权」的兑换物，而按 GitHub 的社区规范，用利益换取 star 属于灰色地带。二是对使用者来说，你的 GitHub 账号会和一个第三方网关产生绑定关系，而这个网关的凭据由维护者掌控——README 自己也承认，「滥用会导致全体用户的通道被收紧」。

## 该不该用

| 可以用 | 不要用 |
|---|---|
| 隔离的玩具环境，试某个模型的行文风格 | 任何写着公司代码、客户数据的机器 |
| 学习 dsh 插件怎么写、看一个高完成度实现 | 要交付的工作、要长期依赖的流程 |
| 临时验证一个想法，用完就删 | 把它的转发端口暴露到局域网之外（README 自己都在拦） |

如果你只是想试试免费模型，更稳的路径是自己去 OpenCode Zen 或 Kilo 注册、拿自己的额度、配自己的 key。多花十分钟，但数据边界和账号风险都清楚得多。

## 一点判断

它暴露的是一个结构性问题：**免费额度是发给「人」的，不是发给「agent」的。**

过去两年，各家用免费额度换注册、换活跃，前提是使用速度受人类打字速度限制。当 agent 能以插件形式每小时发几千个请求，免费额度就从「拉新成本」变成了「被薅的漏洞」。这类插件必然出现，也必然在被发现后关闭——区别只在于谁在关闭前把自己的代码和数据喂了进去。

第二件值得记的事：**读它的 README 比装它更有价值**。那份文档罕见地把「免费车道的成本结构」「上游会怎么拦」「你的数据去哪」写清楚了，连「哪个模型卡声明会记录 prompt」都标了出来。它无意中成了一份很好的反面教材，让你知道所有「免费模型」背后，钱和风险最终落在谁头上。

所以这篇放在这个集合里，不是推荐，是**标记**：你迟早会在时间线上刷到它，先知道它是什么、代价在哪，比事后补课便宜。
